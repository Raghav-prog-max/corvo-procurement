# Business decisions and ambiguities

- Requirement grouping is anchored to the first line, not a rolling chain. Creation timestamps sort chronologically, then PR number and numeric line. Calendar-day clubbing and need-by windows are inclusive. PO consolidation uses elapsed hours, anchored to the first requirement. The input's timezone-free timestamps are interpreted consistently as UTC for arithmetic; all kit timestamps share a timezone, so differences are preserved.
- Each processing run is a deterministic simulation from the imported register's consumption snapshot. It reserves contract ceiling within that run in requirement order, including unapproved proposed POs. Replaying another batch does not permanently consume ceilings. This makes blind-test comparisons repeatable; production purchasing would need a transactional reservation ledger across batches.
- Whole requirements must fit a contract; no partial allocation across contracts. Ties use contract ID. If all ceilings are exhausted, valuation still uses the lowest applicable rate. Valuation history includes any supplier's historical PO as section 3 does not restrict it; direct-PO eligibility and ranking use only currently Active suppliers. Capex never consumes contract ceiling because it routes to sourcing first.
- Source valuation and PO reference prices can differ, as specified: group value follows section 3; emergency/spot PO price follows preferred supplier reference price. Monetary comparisons use rate precision, ceiling comparisons are rounded to paise, and displayed/exported requirement values use two decimals.
- Preferred score: 40 × PO count / highest supplier count for that item + 25 × recency bucket (1 within 90 days, 0.5 within 365, 0 otherwise) + 15 for any commenced contract + 10 × on-time percentage / 100 + 10 × quality / 5. Frequency is normalized within the item. Ties use supplier ID. Eligible history is strictly before the as-of calendar date, within inclusive 548 days. Same-day POs are excluded to avoid using future purchases. Expired contracts qualify, future contracts do not. If no historical PO exists, use the most recently started contract rate. Category top-ups rank by delivery/100 + quality/5, then supplier ID. Never pad the list with ineligible suppliers when fewer than 3/5 exist.
- Item codes take precedence. Invalid codes become new items, never silently remapped from their descriptions. Text matching expands common procurement abbreviations, normalizes punctuation and suffixes, requires identical numeric specifications, and rejects ambiguous matches. Unknown items stay separate and need a positive estimated price. Chat asks for a code or estimate rather than inventing an item. Relative dates currently prompt for an explicit ISO date to avoid deadline ambiguity.
- Zero/negative quantities, missing identities, duplicate PR identities, invalid dates, unknown plants, UOM mismatches and missing estimates for new items use NOT_PROCESSED with a reason. No unsupported UOM conversion is invented. Every input line remains in the CSV export. Duplicate identities are invalid from their second appearance onward.
- Policy effective date is compared to the requirement date. Lines crossing a policy-version boundary form separate requirements. For blind-test replay, buyers may explicitly select any installed version. Rules are data, but operators and supported outcome types are an explicit safe vocabulary. Unsupported prose is rejected for manual review, rather than silently partially activating an amendment.
- PDF extraction proposes structured contract data for buyer review. Existing register contracts cannot be overwritten by PDF imports, preventing consumed values from being reset. PDF-only contracts start at zero consumption. Image-only PDFs need external OCR/manual entry.
- Approvals create internal document records, with run-scoped PO identities to avoid collisions across runs. Each requirement is approved separately; consolidated PO identifiers remain shared. No supplier messages or actual external POs are sent. Overrides are restricted to sourcing outcomes and require comments; unrestricted PO overrides would need explicit pricing, supplier and ceiling validation. Original decisions are retained in the audit record.
- This deployment has one owner identity, no employee login or role-based authorization. Local development is a JSON-backed adapter; hosted persistence is D1 SQLite. The workspace uses a single optimistic aggregate row for simplicity and rejects concurrent changes rather than losing them. Source is data-free; hosted task data stays private.
